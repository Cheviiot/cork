# Сборка и разработка

## Контейнер

Сборочные зависимости ставятся в Distrobox, а не на хост. Контейнер называется
`cork-dev`, образ — Fedora 44 (тот же, что у `aeonlc-build`, и он же уже есть
локально).

```sh
distrobox create --name cork-dev --image registry.fedoraproject.org/fedora:44 --yes
distrobox enter cork-dev
```

Внутри контейнера, один раз:

```sh
sudo dnf install -y --setopt=install_weak_deps=False \
  gcc-c++ cmake ninja-build git perl-core perl-IPC-Cmd python3 \
  zip unzip tar xz zstd pkgconf-pkg-config \
  autoconf automake libtool autoconf-archive bison flex patch file which \
  clang lld llvm

# Рантаймы санитайзеров в Fedora лежат отдельными пакетами; без них пресеты
# linux-asan и linux-tsan не линкуются.
sudo dnf install -y libasan libubsan libtsan
```

`autoconf-archive` нужен обязательно: без него часть портов vcpkg не
конфигурируется.

`clang`, `lld` и `llvm` нужны для сборки Wine. Именно `llvm`, а не только
`clang`: PE-часть Wine собирается своим компилятором, и `winebuild` зовёт
`dlltool` для импорт-библиотек. Отдельного `dlltool` в Fedora нет, но
`find_tool` в `tools/winebuild/utils.c` умеет падать на `llvm-dlltool`, который
лежит именно в пакете `llvm`. Без него сборка валится на первой же
импорт-библиотеке сообщением `cannot find the 'dlltool' tool`.

## Сборка

```sh
. tools/toolchain_env.sh
cmake --preset linux-release
cmake --build --preset linux-release
ctest --preset linux-release
```

Собранные бинарники запускаются **внутри контейнера**, а не на хосте: в
Fedora 44 glibc 2.43, на хосте ALT — 2.38, и `./build/.../test_download` на
хосте падает с `version GLIBC_2.43 not found`. Это не частность, а
подтверждение того, почему релизы должны собираться в CI на базе с низким
glibc, а контейнер годится только для разработки и проверок.

Пресеты: `linux-debug`, `linux-release`, `linux-asan` (address+undefined),
`linux-tsan` (thread). Каталог сборки — `build/<пресет>`, зависимости vcpkg —
`build/dependencies`, чтобы не засорять общий клон.

## Эталон для читателя MSI

`tools/msi_probe.py` — независимая реализация разбора CFBF и таблиц
установщика на Python. Она существует не как черновик, а как вторая пара
глаз: формат устроен так, что почти каждая ошибка даёт не отказ, а
правдоподобный мусор — имена таблиц из тех же букв, строки из соседних
ячеек пула. Расхождение между двумя реализациями находит то, чего не
находит ни один отдельный прогон.

```sh
# сводка по корпусу: таблицы, архивы, атрибуты
tools/msi_probe.py survey ~/.cork/store/blobs/sha256/*/*

# методы сжатия и наличие архивов с продолжением
tools/msi_probe.py cabs <файлы.cab>

# построчная сверка с читателем на C++
tools/msi_probe.py dump пакет.msi > a
CORK_MSI_DUMP=пакет.msi ./build/linux-debug/tests/test_msi > b
diff a b
```

Тот же тест без переменной окружения работает на пакете, собранном из
байтов прямо в нём, и в CI идёт без сети и без настоящих .msi.

## Добавление строки в вывод

Граница простая: **stdout переводится, stderr — нет**. Она грубее, чем деление
«текст для человека» против «диагностики», зато видна в коде без рассуждений.
Сообщения об ошибках остаются английскими, потому что уезжают в отчёты и в
поиск по сети.

Строка на stdout добавляется в трёх местах:

1. `src/i18n/messages.hpp`, макрос `CORK_MESSAGES` — имя и английский текст;
2. `src/i18n/messages.cpp`, функция `russian()` — перевод;
3. место вывода — `i18n::say(i18n::Msg::Имя, аргументы...)`.

Пропустить второй шаг не выйдет: `test_i18n` сверяет каталог построчно и
сообщает, сколько строк переведено из скольких. Он же проверяет, что у
перевода ровно те же подстановки `{}`, что у оригинала, — формат берётся из
каталога в рантайме, компилятор его не видит, и лишняя скобка стала бы не
кривым текстом, а исключением посреди работающей установки.

Множественного числа в каталоге нет: в русском форм три, а строк со счётчиками
меньше десятка, поэтому они переписаны так, чтобы согласование не требовалось
(«проверок: 12», а не «12 проверок»).

## Размер сборки Wine

Шестьдесят один процент собранного Wine — это DWARF: 664 МиБ из 1082 МиБ
PE-файлов (замерено на 11.18 с i386 и x86_64). У ELF-части доля ещё выше,
`ntdll.so` худеет вчетверо.

`tools/wine/build.sh` вынимает её в отдельное дерево через
`tools/wine/split-debug.sh`; `--keep-debug` выключает этот шаг. Тот же скрипт
можно запустить на уже собранном дереве, не пересобирая Wine:

```bash
tools/wine/split-debug.sh build/wine-staging/opt/cork-wine
```

Замерено: 1,5 ГБ → 827 МБ, отладочная часть 1,1 ГБ, 4231 файл, 2 мин 53 с.

Строго `--strip-debug`, не `--strip-all`: в PE x86_64 раскрутка стека живёт в
`.pdata` и `.xdata`. Дымовой проверкой их потерю не поймать — ломается только
настоящее исключение, поэтому проверять надо программой, которая бросает и
ловит.

Грабля замера: имя секции длиннее восьми знаков хранится в COFF не само по
себе, а как `/<смещение>` в строковой таблице, поэтому `.debug_info` выглядит
как `/43`. Без разрешения этих имён отладочные секции просто не видны — первый
замер дал 1% вместо 61%.

## Devel-часть Wine

Заголовки Windows и libc++ (70 МБ), импорт-библиотеки `*.a` (77 МБ) и
`winegcc`/`wineg++`/`winebuild`/`widl`/`wrc`/`wmc` — это около 149 МБ, которые
на машине пользователя не нужны ни разу: PE-хелпер собирается здесь, в CI, и
едет вшитым в бинарник `cork`.

`tools/wine/build.sh` уносит их в отдельное дерево через
`tools/wine/split-devel.sh`; `--keep-devel` выключает этот шаг. Тот же скрипт
работает и на уже собранном дереве:

```bash
tools/wine/split-devel.sh build/wine-staging/opt/cork-wine
```

Состав задан не кодом, а списком в `wine/split-rules.txt`: строка «класс
образец», побеждает первое совпадение, классы — `runtime`, `sdk`, `drop`.
**Файл, не подошедший ни под одно правило, останавливает сборку.** Это и есть
главное здесь, а не мегабайты. До сих пор devel попадал в артефакт побочным
эффектом `make install`, его состав нигде не был закреплён, и всякая правка в
дереве Wine молча меняла то, что уезжает пользователю — в ту и в другую
сторону. Список превращает состав в решение.

Порядок при добавлении строки обратный привычному: сначала убедиться, что без
файла проходит приёмочная матрица, и только потом переводить его из `runtime`.

## Отклонения от конвенций AeonLC

AeonLC требует `cmake_minimum_required(VERSION 4.4.3)` и пресеты версии 10,
подтягивая пиннутый cmake из `~/Project/.workspace/toolchains`. Здесь взята
планка 3.28 и пресеты версии 8: в контейнере стоит cmake 4.3.0, на хосте
3.31.7, на раннерах GitHub около 3.31, и требовать предварительной установки
своего cmake значит сделать «собрать одной командой» неправдой.

По той же причине не используется `VCPKG_CHAINLOAD_TOOLCHAIN_FILE` с пиннутым
LLVM: берётся компилятор контейнера. Если для статической линковки понадобится
конкретный тулчейн, это будет отдельное осознанное решение, а не наследование.
