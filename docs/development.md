# Сборка и разработка

## Контейнер

Сборочные зависимости ставятся в Distrobox, а не на хост. Контейнер называется
`cork-dev`, образ — Fedora 44 (тот же, что у `aeonlc-build`, и он же уже есть
локально).

```sh
distrobox create --name cork-dev --image registry.fedoraproject.org/fedora:44 --yes
distrobox enter cork-dev
```

Внутри контейнера, один раз:

```sh
sudo dnf install -y --setopt=install_weak_deps=False \
  gcc-c++ cmake ninja-build git perl-core perl-IPC-Cmd python3 \
  zip unzip tar xz zstd pkgconf-pkg-config \
  autoconf automake libtool autoconf-archive bison flex patch file which \
  clang lld llvm

# Рантаймы санитайзеров в Fedora лежат отдельными пакетами; без них пресеты
# linux-asan и linux-tsan не линкуются.
sudo dnf install -y libasan libubsan libtsan
```

`autoconf-archive` нужен обязательно: без него часть портов vcpkg не
конфигурируется.

`clang`, `lld` и `llvm` нужны для сборки Wine. Именно `llvm`, а не только
`clang`: PE-часть Wine собирается своим компилятором, и `winebuild` зовёт
`dlltool` для импорт-библиотек. Отдельного `dlltool` в Fedora нет, но
`find_tool` в `tools/winebuild/utils.c` умеет падать на `llvm-dlltool`, который
лежит именно в пакете `llvm`. Без него сборка валится на первой же
импорт-библиотеке сообщением `cannot find the 'dlltool' tool`.

## Сборка

```sh
. tools/toolchain_env.sh
cmake --preset linux-release
cmake --build --preset linux-release
ctest --preset linux-release
```

Собранные бинарники запускаются **внутри контейнера**, а не на хосте: в
Fedora 44 glibc 2.43, на хосте ALT — 2.38, и `./build/.../test_download` на
хосте падает с `version GLIBC_2.43 not found`. Это не частность, а
подтверждение того, почему релизы должны собираться в CI на базе с низким
glibc, а контейнер годится только для разработки и проверок.

Пресеты: `linux-debug`, `linux-release`, `linux-asan` (address+undefined),
`linux-tsan` (thread). Каталог сборки — `build/<пресет>`, зависимости vcpkg —
`build/dependencies`, чтобы не засорять общий клон.

## Эталон для читателя MSI

`tools/msi_probe.py` — независимая реализация разбора CFBF и таблиц
установщика на Python. Она существует не как черновик, а как вторая пара
глаз: формат устроен так, что почти каждая ошибка даёт не отказ, а
правдоподобный мусор — имена таблиц из тех же букв, строки из соседних
ячеек пула. Расхождение между двумя реализациями находит то, чего не
находит ни один отдельный прогон.

```sh
# сводка по корпусу: таблицы, архивы, атрибуты
tools/msi_probe.py survey ~/.cork/store/blobs/sha256/*/*

# методы сжатия и наличие архивов с продолжением
tools/msi_probe.py cabs <файлы.cab>

# построчная сверка с читателем на C++
tools/msi_probe.py dump пакет.msi > a
CORK_MSI_DUMP=пакет.msi ./build/linux-debug/tests/test_msi > b
diff a b
```

Тот же тест без переменной окружения работает на пакете, собранном из
байтов прямо в нём, и в CI идёт без сети и без настоящих .msi.

## Добавление строки в вывод

Граница простая: **stdout переводится, stderr — нет**. Она грубее, чем деление
«текст для человека» против «диагностики», зато видна в коде без рассуждений.
Сообщения об ошибках остаются английскими, потому что уезжают в отчёты и в
поиск по сети.

Строка на stdout добавляется в трёх местах:

1. `src/i18n/messages.hpp`, макрос `CORK_MESSAGES` — имя и английский текст;
2. `src/i18n/messages.cpp`, функция `russian()` — перевод;
3. место вывода — `i18n::say(i18n::Msg::Имя, аргументы...)`.

Пропустить второй шаг не выйдет: `test_i18n` сверяет каталог построчно и
сообщает, сколько строк переведено из скольких. Он же проверяет, что у
перевода ровно те же подстановки `{}`, что у оригинала, — формат берётся из
каталога в рантайме, компилятор его не видит, и лишняя скобка стала бы не
кривым текстом, а исключением посреди работающей установки.

Множественного числа в каталоге нет: в русском форм три, а строк со счётчиками
меньше десятка, поэтому они переписаны так, чтобы согласование не требовалось
(«проверок: 12», а не «12 проверок»).

## Размер сборки Wine

Замерено на `wine-11.18` с `--enable-archs=i386,x86_64`, одной командой
`tools/wine/build.sh` из контейнера `cork-dev`:

| этап | дерево | что уехало в сторону |
|---|---|---|
| после `make install` + Mono | 1,5 ГБ | — |
| минус отладочная информация | 827 МБ | 907 МБ, 1507 файлов из 4231 |
| минус devel | **684 МБ** | 143 МБ, 2359 файлов |

Шестьдесят один процент исходного веса — DWARF. `tools/wine/split-debug.sh`
выносит его в отдельное дерево, `--keep-debug` выключает шаг. Скрипт
запускается и на уже собранном дереве, не пересобирая Wine:

```bash
distrobox enter cork-dev -- tools/wine/split-debug.sh build/wine-staging/opt/cork-wine
```

Именно так, из контейнера. На хосте `llvm-objcopy` не умеет PE и отвечает
`debug directory not found` — раньше скрипт принимал это за «секций нет» и
срезал их, то есть терял. Теперь наличие секций он определяет по самому файлу
через `llvm-objdump -h`, и если они есть, а вынуть не удалось, останавливается,
ничего не тронув.

Строго `--strip-debug`, не `--strip-all`: в PE x86_64 раскрутка стека живёт в
`.pdata` и `.xdata`. Дымовой проверкой их потерю не поймать — ломается только
настоящее исключение, поэтому проверять надо программой, которая бросает и
ловит.

Грабля замера: имя секции длиннее восьми знаков хранится в COFF не само по
себе, а как `/<смещение>` в строковой таблице, поэтому `.debug_info` выглядит
как `/43`. Без разрешения этих имён отладочные секции просто не видны — первый
замер дал 1% вместо 61%.

### Что занимает место на машине пользователя

| | видимый размер | занято на диске |
|---|---|---|
| рантайм | 684 МБ | 684 МБ |
| префикс после `wineboot` | 1,2 ГБ | 124 МБ |
| шаблон | 1,2 ГБ | 3,1 МБ |
| префикс каждой сборочной сессии | 1,2 ГБ | 3,1 МБ |

Разница между колонками — reflink: см. «Префикс и рантайм делят одни
экстенты» в `docs/generations.md`. Правая колонка получена через
`btrfs filesystem du -s` и разницу свободного места; `du` для этого не
годится и показывает левую в обеих.

## Devel-часть Wine

Заголовки Windows и libc++, импорт-библиотеки `*.a` и
`winegcc`/`wineg++`/`winebuild`/`widl`/`wrc`/`wmc` — 2359 файлов на 143 МБ,
которые на машине пользователя не нужны ни разу: PE-хелпер собирается здесь, в
CI, и едет вшитым в бинарник `cork`.

`tools/wine/build.sh` уносит их в отдельное дерево через
`tools/wine/split-devel.sh`; `--keep-devel` выключает этот шаг. Тот же скрипт
работает и на уже собранном дереве:

```bash
tools/wine/split-devel.sh build/wine-staging/opt/cork-wine
```

Состав задан не кодом, а списком в `wine/split-rules.txt`: строка «класс
образец», побеждает первое совпадение, классы — `runtime`, `sdk`, `drop`.
**Файл, не подошедший ни под одно правило, останавливает сборку.** Это и есть
главное здесь, а не мегабайты. До сих пор devel попадал в артефакт побочным
эффектом `make install`, его состав нигде не был закреплён, и всякая правка в
дереве Wine молча меняла то, что уезжает пользователю — в ту и в другую
сторону. Список превращает состав в решение.

Порядок при добавлении строки обратный привычному: сначала убедиться, что без
файла проходит приёмочная матрица, и только потом переводить его из `runtime`.

Две ловушки, на которые скрипт уже наступал и больше не наступит. Первая:
образцы разбирались через `set -- $line`, то есть попадали под раскрытие имён
файлов, а `build.sh` к этому моменту стоит в каталоге сборки Wine, где есть
`include/`; правило `sdk include/**` рассыпалось на полторы тысячи слов и
молча выпадало. Из корня репозитория тот же скрипт работал — дефект зависел от
каталога, из которого его позвали. Вторая: перенос шёл по ходу обхода, а о
непокрытых файлах скрипт сообщал в конце, и упавший прогон оставлял дерево
разрезанным пополам. Теперь дерево классифицируется целиком и только потом
трогается.

## Чего в Mono можно было бы не возить (замерено, не сделано)

Mono — 226 МБ из 684 МБ рантайма, самая крупная оставшаяся доля. Прежде чем
её трогать, стоило узнать, что там лежит.

MSBuild действительно исполняется **под Wine Mono**, а не под настоящим .NET:
трасса `openat` обычной сборки `.vcxproj` показывает 1038 обращений внутрь
`share/wine/mono`, включая `libmono-2.0-x86_64.dll`, `mscorlib.dll` и
`etc/mono/4.5/machine.config`. То есть выбросить Mono целиком нельзя.

Дальше два разных наблюдения, и они очень разного качества.

**Структурное, проверяемое без запуска.** В `lib/mono` 2897 файлов, из них
уникальных по содержимому 1577: **95 МиБ — точные дубликаты**. Плюс 103 МБ —
справочные сборки `*-api` пятнадцати версий фреймворка, от `2.0-api` до
`4.8-api`.

**По наблюдению за одним прогоном.** Та же сборка открыла всего 15 файлов
Mono на 17 МБ из 2790 файлов на 226 МБ.

Второе число выглядит соблазнительнее первого и годится хуже. Прореживание
«по тому, что открылось» ломается у пользователя и не ломается у нас: другой
тип проекта, другая задача MSBuild — и отсутствующая сборка всплывает
`TypeLoadException` из глубины чужого кода. Одного прогона для такого решения
мало, а набрать представительный набор пока не на чем.

Дубликаты — другое дело: содержимое совпадает побайтово, поведение измениться
не может, и механизм уже есть — тот же reflink, что и для префикса. Но класть
его некуда: рантайм на машину пользователя пока никак не попадает (см. ниже),
а на дереве сборки reflink не переживёт упаковки в архив. Поэтому замер
записан, а работа отложена до артефакта.

## Как рантайм Wine попадает на машину

На машине разработчика — символической ссылкой: `~/.cork/runtime/<id>`
показывает на `build/wine-staging/opt/cork-wine`. Так правка в сборке Wine
видна сразу, без установки.

Везде остальное — скачиванием. Долгое время его не было вовсе: `cork
download` качал пакеты Microsoft и не знал про Wine ни строки, а сообщение об
отсутствующем рантайме всё равно отправляло именно туда. На чужой машине это
был тупик — человек делал, что сказано, ничего не менялось, и почему, видно
не было.

Обе недостающие части теперь есть.

`wine-release.yml` вызывает тот же `tools/wine/build.sh` вместо своей копии
сборки, то есть публикует ровно то, что проверяется приёмочной матрицей.
Оговорка: воркфлоу запускается только руками и с момента правки ни разу не
прогонялся — проверена его форма, а не работа.

`cork download` ставит рантайм сам, в конце, по закреплённому sha256
(`src/setup/runtime.cpp`). Не отдельной командой: «скачайте ещё вот это» —
ровно тот шаг, который пропускают.

Чего не хватает, чтобы это заработало у человека: **строки в
`wine/runtime-pins.txt`**. Она вписывается рукой по `SHA256SUMS` удачного
прогона воркфлоу, и пока пуста, потому что артефакта, собранного уже новым
воркфлоу, ещё нет. Старые релизы не годятся: в них нет патчей автономности,
одна архитектура и не сделано ни одного разделения — это другое дерево с тем
же именем.

Пока строки нет, `cork download` делает всю остальную работу и говорит на
stderr, что рантайма не будет и его надо собрать. Отказом это не считается:
пакеты скачаны, дерево распаковано, и `install` по ним пройдёт, как только
рантайм появится.

### Что проверяет установка рантайма

Хеш, а не источник. Артефакт лежит на github, и подмена файла по тому же
адресу ничем не отличается от обычной загрузки, кроме содержимого; поэтому
sha256 закреплён в дереве и обновляется рукой человека, а не тем, что ответил
сервер.

Распаковка идёт в `runtime/<id>.unpacking` и переименовывается на место. Плюс
проверка, что в архиве есть `bin/wine`. Оба правила про одно: дерево,
распакованное наполовину, выглядит установленным и не работает, а разбираться
в этом придётся посреди чужой сборки.

Проверяется это `tests/test_runtime.cpp` на локальном HTTP-сервере: удачная
установка с символьной ссылкой на месте, повтор без обращения к сети, чужой
хеш (после него в `runtime/` не остаётся ничего), архив без `bin/wine`,
отсутствие закрепления и разбор списка.

## Что собирает CI и почему одним скриптом

`wine-release.yml` не собирает Wine сам — он ставит зависимости, кладёт в PATH
каталог clang 19 и зовёт `tools/wine/build.sh`. Так определение сборки одно:
подмодуль `wine/src`, серия патчей, `wine/configure-flags.txt`, версия Mono из
исходников, оба разделения.

До этого воркфлоу держал свою копию: клонировал Wine по тегу из поля ввода,
выписывал флаги configure руками, не применял патчей автономности и не делал
ни одного разделения. Копия отстала молча — с одной архитектурой вместо двух,
с Mono 11.2.0 в умолчании против 11.3.0 в дереве, — и публиковала артефакт,
которого приёмочная матрица никогда не видела.

Два следствия, которые стоит знать заранее:

- **Только amd64.** Прежняя матрица собирала ещё и arm64, но именно ту, свою,
  неверную сборку. ARM64-хост отнесён к отложенному срезу; тогда же
  `--enable-archs` придётся убрать из `wine/configure-flags.txt` и выводить из
  архитектуры хоста — сейчас там жёстко `i386,x86_64`.
- **clang ставится версией, но `/usr/bin/clang` больше не перезаписывается.**
  `configure` принимает `x86_64_CC` и `i386_CC` напрямую, и `build.sh`
  выставляет обе из `CORK_PE_CC`. Обе, а не одну: с двумя архитектурами
  PE-часть собирается дважды, и i386 без своей переменной берёт системный
  clang — ровно тот, из-за которого переменная и понадобилась.

Публикуется только рантайм. Devel и отладочная информация уезжают отдельными
артефактами прогона, и имена у них нарочно не подходят под образец
`cork-wine-linux-*`, по которому собирается релиз.

## Что считает хеши и почему не своё

SHA-256 считает OpenSSL через `EVP_*`. Здесь была своя реализация, и довод
за неё звучал разумно: OpenSSL приезжает транзитивно вместе с curl, но
завязывать на его версию проверку целостности всего, что мы скачиваем, не
хочется — алгоритм зафиксирован стандартом навсегда, а API OpenSSL между
ветками меняется.

Довод не выдержал замера. Два гигабайта одним потоком на этой машине:

| | скорость |
|---|---|
| своя реализация | 381 МБ/с |
| OpenSSL | 2160 МБ/с |

В 5,7 раза, и разница не в качестве кода: у процессора есть инструкции
SHA-NI, и OpenSSL их берёт. Догонять её своими силами значит написать и
отлаживать ассемблер под несколько микроархитектур ради того, что уже лежит
в бинарнике.

Цена — ноль: `libcrypto` и так статически внутри, её тянет `curl[ssl]`.
Новой зависимости не появилось.

Видно это там, где считается много: `doctor --deep` проходит всё дерево
поколения, и он **был 21–27 с, стал 4,9 с**. Плюс каждый скачанный пейлоад
при `cork setup`.

Векторы NIST в тесте остались. Они теперь проверяют не алгоритм, а то, что
мы правильно его позвали, — и это ровно то, что здесь может сломаться.

MD5 остался своим, и это не непоследовательность. Он нужен для одной таблицы
`MsiFileHash` внутри `.msi`, аппаратного ускорения у MD5 нет, выигрыш был бы
около полутора раз, а в сборке OpenSSL с ограничениями (FIPS) его может не
оказаться вовсе. Менять ради этого рабочий код не стоит.

## Отклонения от конвенций AeonLC

AeonLC требует `cmake_minimum_required(VERSION 4.4.3)` и пресеты версии 10,
подтягивая пиннутый cmake из `~/Project/.workspace/toolchains`. Здесь взята
планка 3.28 и пресеты версии 8: в контейнере стоит cmake 4.3.0, на хосте
3.31.7, на раннерах GitHub около 3.31, и требовать предварительной установки
своего cmake значит сделать «собрать одной командой» неправдой.

По той же причине не используется `VCPKG_CHAINLOAD_TOOLCHAIN_FILE` с пиннутым
LLVM: берётся компилятор контейнера. Если для статической линковки понадобится
конкретный тулчейн, это будет отдельное осознанное решение, а не наследование.
