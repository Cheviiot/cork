# Поколения, состояния и проверка

Документ описывает раскладку на диске и то, почему установка устроена именно
так.

## Раскладка

Всё лежит под `$CORK_HOME` (по умолчанию `~/.cork`):

```
~/.cork/
  store/blobs/sha256/<aa>/<hex>   скачанные пейлоады, адресуемые содержимым
  staging/<token>/                поколение, которое сейчас собирается
  toolchains/<name>-<digest>/     опубликованные поколения
  toolchains/current              символическая ссылка на одно из них
  runtime/<wine-id>/              своя сборка Wine
  prefix/<wine-id>/               префикс Wine
  locks/                          файлы блокировок
  run/<pid>/                      временные файлы одного запуска инструмента
```

Внутри поколения:

```
  bin/<arch>/                обёртки инструментов и копия самого cork
  bin/cork-helper.exe        PE-половина обёртки, выложенная из вшитой копии
  share/cork-toolchain.cmake файл тулчейна для кросс-сборки на CMake
  cork.json, receipt.json    конфигурация и фактический состав
```

На PATH кладётся `toolchains/current/bin/<arch>`; на файл тулчейна указывает
`CORK_TOOLCHAIN_FILE`, который выводит `cork env`. Файл лежит в поколении, а не
один на всех: поколений бывает несколько, и общий файл после следующей
установки указывал бы не туда.

## Почему поколение собирается в стороне

Очевидный способ — распаковать всё сразу в конечный каталог, а готовность
определять наличием какого-нибудь ключевого файла вроде `bin/wine`. Он не
работает: прерывание в середине оставляет дерево, которое выглядит
установленным. Каталоги на месте, файл есть, проверка довольна, собрать
нечем.

Здесь поколение целиком собирается в `staging/<token>`, проверяется там же и
только потом переименовывается на место. Прерывание на любом шаге оставляет
каталог в `staging/`, который ничем не притворяется: `current` на него не
указывает, `doctor` его не видит, `cork gc` его уберёт.

## Почему публикация атомарна

В имя каталога поколения входит начало дайджеста его дерева, поэтому
публикация — это всегда `rename` в имя, которого ещё нет. Переключение
`current` — создание символической ссылки под временным именем и `rename`
поверх старой, то есть атомарная замена. Момента, в который `current`
указывает в никуда, не возникает.

Следствие: одно и то же дерево, собранное дважды, получает одно и то же имя.
Повторная установка не перезаписывает проверенное, а просто переставляет
`current`.

Второе следствие: `staging/` и `toolchains/` обязаны лежать на одной файловой
системе. Если это не так, `rename` вернёт `EXDEV`, и публикация откажет вместо
того, чтобы молча превратиться в долгое копирование, прерывание которого
оставляет полудерево.

## Состояния

Состояние читается из журнала в `receipt.json`, а не выводится из файловой
системы. Каждое следующее требует предыдущего, назад ходить нельзя.

| Состояние | Что означает |
|---|---|
| `resolved` | выбор пакетов сделан, его дайджест записан |
| `fetched` | каждый пейлоад лежит в хранилище и проверен по sha256 |
| `staged` | всё распаковано и перенесено, дерево собрано |
| `verified` | дайджест дерева посчитан, быстрые проверки прошли |
| `published` | поколение переименовано на место, `current` указывает сюда |
| `buildable` | пробник скомпилирован и скомпонован (пока не реализовано) |

`published` записывается в receipt **до** переименования. Это намеренно: если
публикация не состоится, каталог останется в `staging/`, где его никто не
ищет, — а опубликованное дерево обязано с первой же секунды нести верное
состояние.

## Receipt

`receipt.json` хранит не намерение, а результат: из какого манифеста, какие
пейлоады по каким хешам, сколько файлов откуда распаковано, какие патчи с
какими хешами до и после, дайджест дерева, состав Wine и журнал состояний.

Отдельно записываются две величины: сколько в дереве Wine символьных ссылок и
сколько файлов в сборке Mono. Они выделены не для красоты. Это ровно те две
вещи, которые разваливаются молча: распаковщик, не умеющий символьные ссылки,
записывает их обычными файлами с путём внутри — и тогда от `lib/mono/4.5` не
остаётся ничего работающего, `MSBuild.exe` не стартует, а дерево при этом
выглядит совершенно целым. Проверке нужно число, с которым можно сравнить;
без него сказать «ссылок стало ноль» не по чему.

Сам receipt исключён из дайджеста дерева: он этот дайджест содержит.

## Проверка

```sh
cork doctor           # быстро: receipt, конфигурация, ключевые файлы, состав Wine
cork doctor --deep    # плюс полный обход дерева против записанного дайджеста
cork doctor --build   # плюс настоящая сборка пробника на каждую цель
```

Уровни вложены: `--build` делает и то, что делает `--deep`. Это осознанно —
«собирается» без «дерево целое» означало бы, что пробник собрался, а порча
лежит в заголовке, которого он не трогает.

Быстрый уровень не читает дерево целиком, поэтому не заметит правку файла того
же размера. На то и есть глубокий; на семи гигабайтах он занимает около минуты.

Тринадцать сценариев повреждений проверяются в CI на синтетическом дереве, без
MSVC, Wine и сети — см. `tests/test_doctor.cpp`. Среди них подмена хелпера с
сохранением размера, символьные ссылки Wine, записанные обычными файлами,
выпотрошенный Mono и receipt чужой версии схемы.

## Конфигурации Release и Debug

Выпускная сборка запускается сразу: `vcruntime140.dll` и `ucrtbase.dll` Wine
отдаёт как builtin. Отладочная (`/MDd`, то есть конфигурация Debug по
умолчанию) — нет, и её библиотеки лежат в двух разных местах:

| Библиотека | Откуда |
|---|---|
| `msvcp140d.dll`, `vcruntime140d.dll`, `vcruntime140_1d.dll` | `VC/Redist/MSVC/<ver>/debug_nonredist/<arch>/Microsoft.VC<NNN>.DebugCRT` |
| `ucrtbased.dll` | `Windows Kits/10/bin/<sdkver>/<arch>/ucrt` |

Оба каталога попадают в `WINEPATH` последними: компилятору они не нужны, а
подмешивать отладочные библиотеки в поиск раньше выпускных незачем.

Первый из них не выводится формулой, а ищется при установке по наличию
`vcruntime140d.dll` и записывается в `cork.json` как `targets.<arch>.debug_crt`:
в имени каталога стоит номер набора инструментов, а версия редиста не обязана
совпадать с версией компилятора, и формула из этих двух предположений сломалась
бы молча — программа просто не запустилась бы.

## Сессии сборки

Префикс Wine — изменяемое состояние: реестр, `system32`, службы. Две
параллельные сборки в одном префиксе мешают друг другу, а брошенный процесс
Wine предыдущей сборки достаётся следующей. Поэтому каждая сборка получает
свой префикс.

Ключ сессии выводится из корня сборочного дерева — первого каталога вверх, где
лежит `build.ninja`, `CMakeCache.txt`, `Makefile` или `.git`. Так все вызовы
компилятора одной сборки попадают в одну сессию, а разные проекты не делят
префикс. Переопределяется через `CORK_SESSION`.

```sh
cork run -- ninja          # сессия создаётся и сносится вместе с командой
cork run -- ./app.exe      # то же, но запускается собранное — через Wine
cork session list          # что сейчас есть
cork session stop [ключ]   # убрать; отказывается трогать занятую
cork session kill [ключ]   # убрать, погасив её wineserver
```

Имя команды, оканчивающееся на `.exe`, `cork run` запускает через Wine в
префиксе той же сессии, всё остальное — как обычную программу. Без этого
кросс-компиляция проверяема наполовину: собралось, а запускается ли —
неизвестно.

Вложенный `cork run` сессию не сносит. Признак простой: если `CORK_SESSION`
уже стоял в окружении, значит её завёл кто-то другой — объемлющий вызов или
человек руками, — и убирать её не его дело. Иначе сборка, внутри которой есть
свой `cork run`, разваливалась бы на середине: внутренний вызов вынимал бы
префикс из-под внешнего.

Точного признака «сборка закончилась» не существует: сборочная система об этом
никому не сообщает. Поэтому способов три — `cork run`, который владеет
временем жизни явно, ручные `stop`/`kill`, и сборка мусора по возрасту при
следующем запуске. `cork run` переживает Ctrl-C намеренно: сигнал приходит всей
группе процессов, и если бы он убивал и `cork run`, убирать за прерванной
сборкой было бы некому.

## Шаблон префикса

`wineboot` в пустом каталоге занимает несколько секунд и полгигабайта записи —
на каждую новую сессию. Шаблон убирает эту плату:

```sh
cork template            # из ~/.cork/prefix/<wine-id>
```

Замер на этой машине: первая сборка в новой сессии — 6250 мс без шаблона и
1887 мс с ним, а сам префикс на 617 МБ занимает на диске **ноль байт**, потому
что клонируется разделением экстентов.

Готовый префикс переносимым не является, и это главное, ради чего команда
существует отдельно. `wineboot` оставляет в нём следы того, кто и где его
создал: ссылки `Documents`, `Desktop` и другие указывают в домашний каталог
создателя (в том числе глубоко в `AppData`), реестр хранит эти пути и путь, из
которого ставился Wine Mono, `dosdevices` полон ссылок на устройства этой
машины, а профиль назван именем создателя.

Поэтому шаблон делается в два шага: деперсонализация убирает следы, гейт
переносимости проверяет, что их не осталось. Гейт обязателен — он единственное,
что не даёт непереносимости просочиться в поставку, и найденное им означает
отказ, а не предупреждение. Профиль в шаблоне назван нейтрально; имя текущего
пользователя ему возвращается при создании сессии, вместе с правкой реестра —
иначе `TEMP` указывал бы в несуществующий каталог.

На файловой системе без reflink копия стоит настоящие полгигабайта. Об этом
говорится один раз, с предложением `CORK_PREFIX_MODE=shared` — один префикс на
все сборки, ценой того, что параллельные сборки снова его делят.

## Почему шаблон стареет и чем это видно

Wine кладёт в префикс `.update-timestamp` — время правки `wine.inf` того
дерева, которым префикс создавали. Не совпало — при каждом запуске
поднимается `rundll32 setupapi,InstallHinfSection` и прогоняет `wine.inf`
заново.

Ничего при этом не ломается, и в выводе не появляется ничего. Просто каждая
сессия дорожает на десятки секунд, а причину узнать неоткуда. Замерено на
шаблоне, отставшем от runtime на девять часов: `hello-c` 36 с против 2 с,
`static-lib` 15 с против 1 с, `doctor --build` 118 с против 24 с.

Поэтому `cork doctor` сравнивает эти два времени и предупреждает, а
`cork template` поднимает исходный префикс заново, если тот отстал: иначе
команда делала шаблон из устаревшего префикса и закрепляла задержку навсегда.

### Реестр пишет wineserver, а не wineboot

Самая дорогая грабля этого места. `wineboot --init` возвращает управление
раньше, чем `system.reg`, `user.reg`, `userdef.reg` и `.update-timestamp`
появятся на диске: их пишет `wineserver`, когда завершается, а он висит ещё
несколько секунд после.

Префикс в этот момент выглядит готовым — есть `dosdevices`, есть `drive_c`, —
и не хватает ровно четырёх файлов в корне. Шаблон, снятый с него, получается
вообще без реестра, а `cl` в склонированном из такого шаблона префиксе
отвечает `D8037: cannot create temporary il file`, потому что `TEMP` брать
неоткуда. Ни одно сообщение при этом не говорит про реестр.

Поэтому `boot_prefix` дожидается `wineserver -w` и отказывается отдавать
префикс, в котором нет `system.reg`.

Вторая, меньшая доводка: в свежем префиксе нет ни `users/<кто>/Temp`, ни
`windows/temp` — Wine заводит их при первом обращении. `cork template`
создаёт их сам.

### `/Zi /FS` и запуск служб префикса

`/FS` заставляет `cl` работать через `mspdbsrv.exe` — отдельный процесс,
который ведёт запись в PDB. Запустить его `cl` может только там, где службы
префикса уже подняты. Пока они поднимаются, попытка приводит к:

```
a.c: fatal error C1902: Program database manager mismatch; please check your installation
```

Сообщение говорит о несовпадении версий, и это сбивает с толку: ни версии, ни
установка тут ни при чём.

Отсюда правило для сессионного префикса: **его не надо загружать повторно.**
Он клонируется из шаблона, который загружен целиком, и `wineboot` ему не
нужен. Хуже того, вреден — он перезапускает службы, и первая же компиляция
попадает в гонку с их запуском.

Измерено на шести свежих клонах шаблона на вариант, засчитывается первая
попытка:

| что делалось с клоном перед `cl /Zi /FS` | успехов |
|---|---|
| ничего | 6 из 6 |
| `wineboot --init` | 4 из 6 |
| `wine winepath` со stdio в `/dev/null` | 6 из 6 |

Поэтому `bootstrap_prefix` в `src/exec/runner.cpp` зовёт `wineboot` только
тогда, когда в префиксе нет `system.reg`, то есть он и правда пуст. В
остальных случаях он лишь запускает одну пустяковую программу Wine — ровно
затем, зачем прогрев и был заведён: чтобы службы стартовали от процесса со
stdio в `/dev/null`, а не от первого настоящего вызова инструмента, чьи
конвейеры они иначе удержат открытыми навсегда.

Для пустого префикса остаётся вторая половина того же правила: реестр пишет
wineserver при выходе, а не `wineboot` (раздел выше), поэтому после
`wineboot --init` идёт `wineserver -w`.

Проверяется скриптом `tools/wine/check-fs.sh <каталог сборки Wine>`, который
ставит опыт единственным годным способом — на свежих префиксах, по первым
попыткам и с подсчётом успехов, а не одним запуском.

### Почему mspdbsrv поднимается заранее, а не первым `cl`

Второй отказ того же места, и виден он только на настоящей сборке. Когда
`C1902` ушёл, сборка из девяти файлов через ninja стала падать иначе:

```
main.c(20): fatal error C1090: PDB API call failed, error code '23': (0x000006BA)
```

`0x6BA` — это `RPC_S_SERVER_UNAVAILABLE`: сервер PDB пропал посреди работы.

Причина в том, что сервер один на всю сборку, а job — свой у каждого вызова
инструмента. Если `mspdbsrv.exe` поднимет первый же `cl`, сервер окажется в
job **этого** вызова и умрёт вместе с ним по `KILL_ON_JOB_CLOSE`. Остальные
`cl`, которые в это время пишут в тот же PDB, теряют его на полуслове. На
одном файле этого не видно вовсе: терять сервер некому, и потому первая
версия «виноват job» была отвергнута — её проверяли одним `cl`.

Поэтому сервер поднимает сам cork: `mspdbsrv.exe -start -spawn`, вне
какого-либо job и со stdio в `/dev/null`. Отсоединённо — `-start -spawn` не
завершается, это и есть сам сервер.

Не при заводе сессии, а при первом вызове, в аргументах которого есть `/FS`.
Разница существенная: сервер не выходит сам, пока жив префикс сессии, — и
сессия, которая никогда не собирала с `/FS`, иначе держала бы его до сборки
мусора ни за чем. Замерено: после компиляции без `/FS` серверов ноль, после
компиляции с `/FS` — один.

Отсюда же следствие для сноса сессии: в её префиксе теперь может жить
процесс, который сам не выйдет никогда. Поэтому `close_session` гасит
префикс всегда, а не только при `--force`, как было раньше.

### `CORK_JOB=off`

Все процессы Windows, которые порождает инструмент, держатся в Job Object с
`KILL_ON_JOB_CLOSE`: это единственное, что ловит потомков, ушедших из группы
процессов Unix через `setsid()`. `CORK_JOB=off` эту гарантию снимает —
переменная нужна была, чтобы проверить, не job ли виноват в отказе `/FS`
(в `C1902` — нет, в `C1090` — да, см. выше), и остаётся как лазейка на
случай инструмента, которому job мешает.
Сама она не включается никогда: с ней брошенный процесс Wine переживает
сборку и достаётся следующей.

### Как это искалось, и чего это стоило

Здесь стоит записать не только ответ, но и дорогу к нему: шесть объяснений
подряд оказались неверными, и каждое выглядело убедительно.

| версия | чем опровергнута |
|---|---|
| Job Object уносит `mspdbsrv` | `CORK_JOB=off` не меняет `C1902` — но для `C1090` версия верна, см. выше |
| зависит от нагрузки машины | воспроизводится при load average 1,5 |
| шаблон префикса непригоден | его клон без прогрева проходит 6 раз из 6 |
| лечится подменой `msvcp140_atomic_wait` | на двух свежих префиксах разницы нет |
| Wine собран без gnutls/gssapi/krb5 | пересобран с ними — отказ прежний |
| реестр не дописан, нужен `wineserver -w` | верно для пустого префикса, но клон шаблона и без того с реестром |

Первые пять росли из одной методической ошибки. **Префикс, в котором хоть раз
прошла компиляция с `/FS`, держит выживший `mspdbsrv` и после этого проходит
всегда.** Замер, поставленный в таком префиксе, показывает успех независимо
от того, что именно проверяли. Поэтому любой опыт здесь ставится только на
свежем префиксе и засчитывается только первая попытка.

Шестая — из другой, не менее дорогой: она держалась на одном замере на
вариант. Один замер не отличает «починилось» от «повезло»: отказ случается
два раза из шести, и такую разницу одиночный опыт показывает как чистую
победу. Считать успехи из шести стоило начать раньше.

И третья ошибка, из-за которой первая строка таблицы неверна наполовину:
дефект проверялся **не тем случаем**. Версию «виноват job» отвергли, потому
что одиночный `cl` отказывает и без job. Это правда — и это ничего не
говорит о сборке из девяти файлов, где job действительно уносит `mspdbsrv`
из-под соседей. Два разных отказа в одном месте выглядели как один, пока
первый заслонял второй. Проверять надо было тем же, чем дефект был найден:
настоящей параллельной сборкой.

Из-за этого же в истории есть коммит, который записывает предзапуск
`mspdbsrv` вне job как средство, которое **не** помогает. Тогда это было
правдой: `C1902` заслонял `C1090`, и снятие второго не меняло видимого
результата. Средство работает, но только после того, как убран повторный
`wineboot`. Порядок, в котором снимаются два наложившихся отказа, решает,
какой из них покажется неизлечимым.

Версия про пакеты безопасности стоила дороже прочих — пересборки Wine — и
заслуживает отдельной строки. Под `WINEDEBUG=+pipe` отказ сопровождался
четырьмя сообщениями:

```
err:secur32:SECUR32_initSchannelSP no schannel support, expect problems
err:secur32:start_samss Failed to start SamSs service
err:secur32:load_auth_packages Failed to get security packages list: 80090304
fixme:rpc:RpcBindingSetAuthInfoExW unsupported AuthnSvc 10
```

Из них складывалась стройная картина: `cl` говорит с `mspdbsrv` по RPC с
аутентификацией, а в сборке Wine выключены `--without-gnutls`,
`--without-gssapi`, `--without-krb5`. Картина подтверждалась и тем, что
системный Wine Staging, собранный полностью, проходил ту же команду с первой
попытки. Флаги были сняты, Wine пересобран с gnutls и krb5 — **отказ
остался**. Все четыре сообщения оказались следствием того же неподнятого набора служб:
без них не стартует SamSs, без SamSs не читается список пакетов.
В догруженном префиксе та же урезанная сборка перечисляет и `Negotiate`, и
`NTLM`, а `no schannel support` остаётся печататься и ничему не мешает.

Мораль, которая дороже самого дефекта: совпадение сообщения об ошибке с
правдоподобной причиной ничего не доказывает, пока причина не убрана и отказ
не исчез. Сравнение с чужой сборкой Wine отличалось не одним свойством, а
всеми сразу, и потому не годилось в доказательство ни для одного из них.

## MSBuild

`cl` и `link` берут пути из `INCLUDE` и `LIB`, и этого им хватает. MSBuild
ищет и компилятор, и Windows SDK совсем иначе — через реестр Windows, которого
под Wine нет. Свойство `DisableRegistryUse` переводит поиск на переменные
окружения, и дальше приходится выставить всё, что он рассчитывал найти в
реестре: `VCInstallDir_<N>`, `WindowsSdkDir_10`, `VCToolsVersion` и остальное
из `src/exec/msbuild.cpp`. У каждой записи там указан отказ, который она
гасит, — набор добыт отладкой, и без объяснений он через полгода выглядит
случайным.

Два места, где приходится вмешиваться в саму команду:

- **`/p:WindowsTargetPlatformVersion`.** Единственное свойство, которому не
  хватает переменной окружения: большинство старых `.vcxproj` записывают его
  прямо в `PropertyGroup`, а явное присваивание в проекте всегда сильнее
  унаследованной переменной. Глобальное свойство из командной строки проект
  перебить не может — а SDK у нас установлен ровно один, и собираться надо
  против него, а не падать из-за версии, вписанной когда-то на другой машине.
- **`/nodeReuse:false`.** Узлы повторного использования MSBuild намеренно
  переживают породивший их процесс и ждут следующего вызова. Такой узел
  остаётся в префиксе сессии, а прерванная сборка способна оставить его с
  полуоткрытым каналом — он не умирает, а зависает навсегда, отвечая на каждый
  следующий вызов ошибкой, никак не связанной с происходящим.

Оба ставятся только если вызывающий не задал их сам.

## Наборы инструментов и старые проекты

Установлен ли `PlatformToolset`, MSBuild решает проверкой наличия каталога
`Platforms/<arch>/PlatformToolsets/<имя>` — обычным обращением к диску, на
которое переменные окружения не влияют. Пакет Microsoft кладёт туда запись
только для скачанного поколения, поэтому проект, сохранённый под Visual Studio
2019, отвергается сразу, хотя собрался бы без единой правки.

Отсюда два разных механизма, и путать их не надо.

**Настоящие наборы.** Их можно поставить несколько сразу, повторив ключ:

```sh
cork download --accept-license --msvc-version 18.10 --msvc-version 16.11
```

Первый становится основным, остальные ложатся рядом — раскладка
`vc/tools/msvc/<версия>/` рассчитана на это, Microsoft так и хранит их.
Проект, привязанный к v142, тогда собирается настоящим v142. Доступны v141
(14.16), v142 (14.29) и множество версий v143; v140 и старше в манифесте
Visual Studio 18 нет вовсе.

**Подмена.** Для имён, под которыми настоящего набора нет, `install` заводит
символьную ссылку на тот, что есть. Файлы набора не содержат номера версии,
поэтому это настоящий алиас, а не расходящаяся копия.

Подмена делается **только для v140, v141, v142 и v143**. Все они и v145 — это
поколение 14.x, и Microsoft с Visual Studio 2015 держит между ними бинарную
совместимость: объектный файл от одного линкуется с библиотекой от другого.
Проект может не собраться из-за строгости нового компилятора, но если
собрался — результат корректен.

Для v90, v100, v110 и v120 подмены нет, и это сознательно. Это 9.0, 10.0, 11.0
и 12.0 — другие ABI, и выданный вместо них 14.x дал бы двоичный файл,
несовместимый с библиотеками той эпохи, причём молча. Вместо этого MSBuild
говорит прямо:

```
error MSB8020: The build tools for Visual Studio 2013 (Platform Toolset =
'v120') cannot be found.
```

## Цель x86

Собирается так же, как x64 — достаточно взять обёртки из `bin/x86`:

```sh
export PATH=~/.cork/toolchains/current/bin/x86:$PATH
cl /nologo a.c /Fea32.exe      # PE32 executable, Intel 80386
```

Чтобы такой файл ещё и **запускался** под нашим Wine, он собирается с
`--enable-archs=i386,x86_64`. Без i386 32-битный `.exe` компилируется и
линкуется, но при запуске Wine не находит `syswow64/ntdll.dll` и падает до
`main`. Для кросс-компиляции этого хватило бы, для проверки собранного на
месте — нет.

## Сборка мусора

```sh
cork gc                          # каталоги сборки и сессии старше суток
cork gc --older-than-hours 0     # убрать все брошенные
cork gc --generations 2          # плюс оставить два самых новых поколения
```

Возраст сам по себе ничего не доказывает: распаковка Windows SDK идёт минутами,
и её каталог тоже «старый». Занятость определяется блокировкой `flock`, которую
ядро снимает само при падении держателя, поэтому каталог, которым кто-то занят,
не удаляется, а каталог убитого процесса удаляется сразу. То же и для сессий.

### Почему поколения удаляются только по явной просьбе

Каталоги сборки и сессии `gc` убирает сам, поколения — нет, и `--generations`
приходится назвать руками. Разница не в осторожности, а в том, что о занятости
вообще можно узнать.

У staging и сессии занятость видна: на них есть блокировка. У поколения её нет
и быть не может. Обёртки инструментов лежат **внутри** поколения, и каждая
определяет своё поколение по собственному пути через `/proc/self/exe`, а не
через `current` — именно поэтому переключение `current` не ломает идущую
сборку. Но из этого следует и обратное: идущая сборка держит своё поколение
одним лишь тем, что когда-то запустила из него `cl`, и снаружи этого не видно
никак. Отличить «старое» от «ненужного» отсюда нельзя.

Поколение весит около двенадцати гигабайт, поэтому ошибка дорога в обе
стороны, и решает человек. Текущее поколение не удаляется ни при каком
значении `--generations`: оно не занимает место зря, на него показывает вся
установка.
